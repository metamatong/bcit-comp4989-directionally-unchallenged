destination, follow a route, and recover when location evidence,
destinations, or route conditions change.

The product scope is BCIT Burnaby campus, including indoor and outdoor
navigation where supported by reliable data. Do not restrict the
project by design to SE12 or a single floor.

Inspect available sources and build a connected, demonstrable network.

3. MAP DATA AND PREPROCESSING

Start with the official floor-plan source:
https://www.bcit.ca/facilities/campus-maps/floor-plans/

Inspect the available linked PDFs. Use additional official campus
sources when needed for outdoor connections and document them.

Maintain a source manifest with:
- Source URLs and retrieval dates.
- File hashes for downloaded source files.
- Attribution and relevant usage restrictions.
- Provenance references for extracted records.

Preprocess available maps into editable structured records:
- Buildings, floors, room labels, and landmarks.
- Supported entrances and transitions.
- Corridor and outdoor-path connections.
- A separate node-and-edge routing graph.
- Searchable source text and source references.

Keep map images, searchable information, and routing topology distinct.
Keep floor-plan coordinates separate from geographic coordinates.

Do not invent real room numbers, entrances, corridor connections,
outdoor links, distances, map scale, floor alignment, or accessibility
properties. Validate represented connections against their sources.
Provide a simple way to correct graph and landmark data.

Floor plans are not a dataset of camera views. Do not claim they enable
precise hallway recognition or camera pose estimation.

If reliable campus routing data cannot be prepared, complete the
application using synthetic destinations and a synthetic graph labeled:
“Demo layout — not verified for campus navigation.”

Keep synthetic data separate from verified campus records. A synthetic
demo is an acceptable implementation fallback, but is not evidence of
real-campus navigation accuracy.

During implementation, verify the selected provider's current model
availability, free-tier eligibility, quotas, modalities, and tool

Use a configurable server-side provider adapter. Never expose API keys
in frontend code or assume a coding-assistant subscription supplies

Give the LLM access to preprocessed campus information through
retrieval and typed tools. Use a simple searchable index or structured
lookup first; add more infrastructure only when justified.

Ground campus answers in retrieved records and show useful source
references. If evidence is missing or contradictory, ask for
clarification or report that the answer is unsupported.

Do not require custom model training, fine-tuning, a trained ranker,
a training pipeline, or training accuracy metrics.

Clearly distinguish:
- Preprocessing and indexing.
- Retrieval and map lookup.
- Pretrained OCR or vision.
- LLM interpretation.
- Deterministic route calculation.

Retrieval and feeding information to an LLM are not model training.

5. CORE USER FLOW

1. Open the application and choose “Find my location.”
2. Describe the location, upload a photograph, capture a phone photo,
   or select a labeled demo sample.
3. Extract location evidence and retrieve candidate landmarks.
4. Show the evidence and proposed location for confirmation.
5. Ask a targeted clarification when evidence is ambiguous; abstain
   when evidence is insufficient.
6. Accept a typed or spoken destination and optional arrival time.
7. Resolve the destination, clarify ambiguity, and check conditions.
8. Calculate and display a valid route, next instruction, and an
   estimated travel time where the data supports one.
9. Offer camera guidance and explicit checkpoint confirmation.
10. Apply a relevant simulated blockage and automatically reassess
    the remaining route.
11. Reroute when possible and explain the change and estimated impact.
12. Accept later location evidence or a destination change and reassess.

6. AGENT AND ROUTING

Use one LLM orchestrator with explicit tools and session state.
Multiple runtime agents are unnecessary for this implementation.

Implement a bounded observe–decide–act–reassess loop. The LLM interprets
requests, selects tools, asks clarifying questions, and explains results.

Provide typed tools covering:
- Campus information retrieval.
- Image/OCR evidence analysis.
- Location resolution.
- Destination lookup.
- Route-condition lookup.
- Route calculation.
- Route-impact assessment.
- Simulated disruption reporting and clearing.

Validate tool arguments, outputs, node IDs, edge IDs, and allowed state
changes. Bound iterations and retries, handle timeouts, and prevent
repeated identical calls.

Use Dijkstra or A* for routing. The LLM must never invent navigable
connections or substitute free-form directions for a validated path.

Define route optimality using configured graph costs. Support fastest
routing and avoid-stairs preferences only where metadata permits.
Do not claim wheelchair accessibility without sufficient verification.

Label estimated times and explain their assumptions. Do not fabricate
distance-based ETA precision when source scale is unavailable.

Log observable tool calls, evidence references, state changes, and short
action summaries. Do not request or store hidden chain-of-thought.

7. SIMULATED DYNAMIC CONDITIONS

Use simulated events for the initial implementation.
Camera-assisted blocker detection is deferred.

Store structured events with:
id, affectedEdgeIds, type, status, source, observedAt, expiresAt,
verificationState, reason, and confidence where relevant.

Keep simulated events clearly labeled and separate from real campus
conditions.

Provide working demo controls to:
- Block a segment on the remaining active route.
- Block an unrelated segment.
- Change the destination.
- Clear a blockage.
- Make the destination unreachable.
- Replay closure and reopening scenarios.

Replan only when an event affects the remaining route or materially
changes its cost. Prevent duplicate reports and repeated identical
events from causing reroute oscillation.

Define predictable behavior for duplicate, conflicting, stale, and
expired events. Expiry means evidence needs reassessment; it does not
prove that a path was inspected and found clear.

Provide an explicit no-route state. Never manufacture a connection to
make a destination reachable.

8. CAMERA AND PHONE EXPERIENCE

Provide:
- Photo upload and phone-camera capture.
- Live rear-camera preview when permitted.
- Text and speech destination input, with text fallback.
- Map view, next instruction, landmark label, and small route overview.
- “Confirm checkpoint,” “Correct location,” and “Return to map” controls.
- Clear evidence, uncertainty, and reroute explanations.

Use “Camera guidance” for screen-fixed overlays. Do not claim that an
arrow is anchored to a physical hallway, that the phone continuously
knows its indoor position, or that one photo establishes heading.

When alignment or heading is unknown, show landmark-based instructions
rather than pointing toward an inferred physical doorway.

Keep camera rendering independent of inference. If periodic frame
analysis is enabled, use an initial configurable three-second interval,
compress frames, skip redundant/unusable frames, allow only one request
in flight, and discard stale responses.

Do not invoke the LLM on every frame. Apply request budgets and use
explicit capture when appropriate for quota or privacy constraints.

Never advance location with timers. Use confirmed checkpoints, new
confirmed evidence, or clearly labeled demo controls.

A small marker-anchored AR demonstration is optional when supported.
It must remain separate from campus-wide positioning and must not
block the core camera-guidance implementation.

Document secure-context requirements, phone setup, permission failures,
and device checks that remain unperformed.

9. LIVE AI AND DEMO MODES

Provide two explicit modes:
- Live AI: real provider calls for interpretation and agent decisions.
- Demo: deterministic fixtures and replayed events, visibly simulated.

The entire demo must work without an API key. Fixture responses are not
proof that the live agent works.

Prefer local OCR where practical, lightweight retrieval, and
deterministic routing. Implement caching, budgets, timeouts, backoff,
and usable fallbacks for provider failure or quota exhaustion.

10. INTERFACE, IMPLEMENTATION, AND PRIVACY

Use a polished, uncluttered mobile-first interface:
- Home: destination, optional arrival time, location/photo input.
- Confirm location: evidence and candidate landmarks.
- Navigate: route map, instruction card, and estimated time.
- Camera guidance.
- Demo controls and agent activity panel.

Use large touch targets, readable contrast, and clear empty/error states.
Every visible control must work.

Use the existing project stack where appropriate. Otherwise choose a

Keep photos and audio transient by default. Clearly explain when data
will be sent to an external provider. Do not silently retain media or

11. VERIFICATION AND EVALUATION

Test meaningful integrated behavior:
- Ambiguous locations and destinations require clarification.
- Unknown or insufficient evidence causes abstention.
- Supported photo/sign evidence produces a candidate for confirmation.
- Invalid AI-produced node or edge IDs are rejected.
- Blocked edges are excluded from calculated routes.
- Relevant closures produce valid alternate routes.
- Unrelated closures do not unnecessarily reroute.
- Duplicate, stale, expired, and conflicting events behave predictably.
- An unreachable destination produces a clear no-route state.
- Demo mode works without credentials.
- Camera denial allows upload and manual location selection.
- Unavailable speech input allows text entry.
- Provider failure, quota exhaustion, poor connectivity, and stale
  inference responses have usable fallbacks.

Compare static and dynamic routing on repeatable scenarios. Report
invalid-route avoidance, unnecessary reroutes, routing latency,
inference latency, and provider calls per navigation minute where
actually measured.

Identify hardware, sample sizes, and whether results use real data,
synthetic data, or replayed events. Do not manufacture measurements.

Inspect the mobile interface and verify the end-to-end flow.
Distinguish automated tests, browser checks, physical-device checks,
and on-campus validation.
